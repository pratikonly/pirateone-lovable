Yes, a reverse proxy on Vercel can work. Your visitors' browsers would talk only to your domain, and Vercel's servers (not your users' ISP) would fetch from embed.st. There are a few limits to know about.

Option 1: Vercel rewrites (simplest)

In vercel.json:

json
{
  "rewrites": [
    { "source": "/e/:path*", "destination": "https://embed.st/:path*" }
  ]
}
Then point your iframe at your own domain:

html
<iframe src="/e/your-embed-path" allowfullscreen></iframe>
Vercel fetches the page server-side and returns it from your domain.

Option 2: A serverless/edge function (more control)

Use this if Option 1 breaks. It lets you rewrite HTML and add or strip headers:

js
// api/e/[...path].js
export default async function handler(req, res) {
  const path = [].concat(req.query.path || []).join("/");
  const upstream = await fetch(`https://embed.st/${path}`, {
    headers: { "User-Agent": req.headers["user-agent"] || "" },
  });
  let body = await upstream.text();
  // make absolute links point back through your proxy
  body = body.replaceAll("https://embed.st/", "/api/e/");
  res.setHeader("Content-Type", upstream.headers.get("content-type") || "text/html");
  res.status(upstream.status).send(body);
}
Things that may stop it from fully working:

Root-relative URLs. If the embed loads /assets/player.js, that will resolve to your domain and 404. You'd need to rewrite those paths too (or add a <base> tag).
Other blocked domains. Embeds usually pull video, scripts, or ads from additional domains. If those are also blocked for your users, proxying only the main page won't fix playback. You'd have to proxy those too.
Anti-proxy protections. Some embed hosts check the Referer, Origin, or use Cloudflare bot checks and will reject requests from Vercel's servers.
Vercel limits and rules. The free Hobby plan is non-commercial with bandwidth caps, and proxying video traffic can burn through it fast. Vercel's terms also prohibit using it as an open proxy or to serve infringing content, so make sure you have the right to use and redistribute whatever that embed serves.
Before building anything, quickly check that Vercel can reach it: deploy a rewrite and open yoursite.vercel.app/e/ to see if it loads. If that works, you can handle the relative-path issues next.

The idea: Right now your users' browsers talk directly to embed.st, and their ISP blocks that. Instead, make your users' browsers talk only to your own Vercel domain, which isn't blocked. Vercel's servers then talk to embed.st on their behalf and hand the result back.

Think of it like a middleman: User → your site (Vercel) → embed.st. The ISP only sees the user visiting your site, so the block never applies.

Two versions of this idea:

Simple pass-through (rewrite): Vercel quietly forwards requests from a path on your domain to embed.st. No code logic, just a forwarding rule.
Smart middleman (proxy function): A small piece of code fetches from embed.st, fixes any links inside the page so they also go through your domain, and removes headers that stop it from loading inside your iframe. This handles cases where the simple version breaks.
What can still go wrong:

The embed may load video or scripts from other domains that are also blocked, so those need to go through the middleman too.
embed.st might reject requests coming from Vercel's servers.
Streaming video through Vercel uses a lot of bandwidth and can hit free plan limits.
Vercel's rules don't allow open proxies or serving content you don't have rights to.
Simple summary: hide embed.st behind your own domain so the ISP block can't see it. Try the simple pass-through first, and only use the smart middleman if that breaks.
